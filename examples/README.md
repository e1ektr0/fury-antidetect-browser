# Automation

Driving Fury profiles from a script: what the API is, what it deliberately is
not, and working examples.

## Turning it on

For persistent native Windows execution, startup/shutdown behavior, and remote
administration, see [Windows worker deployment](../docs/windows-worker.md).

The API is **off**. Not off-by-default-in-a-config — nothing binds a port until
you say so:

```bash
FURY_API_PORT=35000 fury-agent serve
```

A local HTTP port is a way into every logged-in profile on the machine, so it
exists because somebody asked for it and not because they installed something.
`0`, an empty value or a typo all leave it off, which is the direction a
mistake should fail in.

Authentication is one token, in one file, created on first use:

```bash
cat "$HOME/Library/Application Support/Fury/api-token"
```

Mode 0600, and file permissions are the whole authorisation story — the port
listens on 127.0.0.1 only. Send it as `Authorization: Bearer <token>`. The
comparison is constant-time, because an attacker controls one side of it.

## The surface

The original six endpoints retain their response shapes. Worker management
adds validated profile and proxy operations using the agent's existing store
and persona validation.

| | | |
|---|---|---|
| `GET`  | `/v1/status`          | is the agent up, and what does it have |
| `GET`  | `/v1/profiles`        | profiles, with which are running |
| `GET`  | `/v1/proxies`         | the proxy pool |
| `GET`  | `/v1/personas`        | the persona catalogue |
| `POST` | `/v1/profiles/start`  | `{"id": "...", "cdp": true}` |
| `POST` | `/v1/profiles/stop`   | `{"id": "..."}` |
| `POST` | `/v1/profiles` | create a profile; returns its generated id |
| `GET` | `/v1/profiles/{id}` | get a profile with runtime state; proxy secrets redacted |
| `PUT` | `/v1/profiles/{id}` | full update of a stopped profile; retains its seed |
| `DELETE` | `/v1/profiles/{id}` | recoverable deletion of a stopped profile |
| `POST` | `/v1/proxies` | create a proxy |
| `PUT` | `/v1/proxies/{id}` | update an existing proxy |

### Creating profiles on a worker

Choose a `persona_id` from `GET /v1/personas`. The write payload is:

```json
{"name":"Pikabu account", "persona_id":"<catalogue id>", "proxy_id":"<proxy id>"}
```

Optional fields include `project_id`, `notes`, `tags`, `status`, `timezone`,
`languages`, `start_urls`, `blocklists`, and validated `overrides`. PUT is a
full replacement of writable settings, not a partial merge. Omitted optional
fields take creation defaults. `fp_seed` and inline `proxy` are not writable;
use `proxy_id`. New identifiers/seeds are generated by the worker, and an
update never changes the established seed. An explicitly proxy-free local
test can set `allow_no_proxy: true`; the default remains false.

Proxy provisioning accepts:

```json
{"name":"Exit", "kind":"socks5", "host":"proxy.example", "port":1080,
 "username":"<username>", "password":"<password>"}
```

Supported kinds are `http`, `https`, and `socks5`. Manage secrets in private
configuration files rather than command-line arguments. Existing list-proxy
behavior includes secrets and is for authorized operators only.

Successful management responses use `{"ok":true,"data":...}`. Input errors
return 400, missing resources 404, and changing/deleting an active profile 409,
with `{"error":"<code>","message":"..."}`. Existing start/stop failures retain
their legacy 400 behavior. Deletion hides a profile; it does not purge browser
data.

[`manage-profile.mjs`](manage-profile.mjs) exercises provisioning, update,
retrieval, CDP launch, stop, and recoverable deletion. Run it on the worker with
Node.js 24, a running agent, and a real Fury core installed:

```powershell
node examples/manage-profile.mjs --token-file "C:\FuryWorker\api-token" --proxy-file "C:\Private\proxy.json"
# Controlled local testing only, explicitly using the host connection:
node examples/manage-profile.mjs --token-file "C:\FuryWorker\api-token" --direct
```

The example always stops and soft-deletes its test profile. A provisioned proxy
is retained in the worker proxy pool for later use.

`start` with `"cdp": true` returns a DevTools endpoint:

```json
{ "ok": true, "data": {
    "pid": 40213,
    "relay_port": 51834,
    "debug_port": 51835,
    "ws_endpoint": "ws://127.0.0.1:51835/devtools/browser/9c1f...",
    "ws": { "puppeteer": "ws://...", "selenium": "ws://..." }
} }
```

The endpoint is under both names because the two libraries people actually use
spell it differently and neither accepts the other's.

## What it is not

**Profile creation is validated.** The worker API uses catalogue personas and
the same override checks as the desktop. It is not an endpoint for injecting
an arbitrary fingerprint configuration.

**CDP is off unless you ask.** `"cdp": true` opens a debugging port on
localhost; without it there is none. A team server can also forbid it per role,
in which case the request succeeds and returns no endpoint — check for
`ws_endpoint` rather than assuming it.

**Automation is detectable and this does not hide that.** `navigator.webdriver`
is false in Fury, but a page can time `console.debug` and see a driver. Measured
on Fury 150, microseconds per call:

| | `"hello"` | 50-key object | 800-key object |
|---|---|---|---|
| no debugger | 3.0 | 2.8 | 2.8 |
| CDP attached, `Runtime.enable` **not** called | 2.8 | 2.8 | 2.8 |
| CDP attached, `Runtime.enable` called | 8.0 | 14.0 | 25.5 |

Attaching costs nothing; `Runtime.enable` costs 2.7x on a string and more as the
argument grows. Every driver calls it. Real Chrome measures the same, so this
detects a driven browser rather than Fury — which is no comfort if the driven
browser is yours. Run it yourself with
[`tools/detect-suite/cdp-timing.py`](../tools/detect-suite/cdp-timing.py).

If a site matters, drive it slowly and like a person, or do not drive it: `cdp`
is off unless you ask, and a team server can refuse it per role.

## The examples

| | |
|---|---|
| [`api.sh`](api.sh) | The original automation API in curl. Start here — it is the shortest path from nothing to a browser you opened from a script. |
| [`playwright_example.py`](playwright_example.py) | `connect_over_cdp`, the usual Python route. |
| [`puppeteer_example.mjs`](puppeteer_example.mjs) | `connect`, the usual Node route. |
| [`rotate.py`](rotate.py) | The thing people actually want: run one job across every profile in a project, one at a time, and never leave a browser open on a failure. |
| [`manage-profile.mjs`](manage-profile.mjs) | Worker profile/proxy provisioning, update, launch, stop, and recoverable deletion. |

The original four use a profile id from the command line; the management example
uses the options documented above. For the original curl example:

```bash
./api.sh                        # lists profiles and their ids
./api.sh <profile-id>           # starts one, opens a page, stops it
```

## Do not put the token in your script

Read it from the file. It is a bearer token for every account on the machine,
and a script is the thing that gets pasted into an issue.
